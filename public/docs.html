ZKTX · ROBINHOOD CHAIN

Private ownership for public tokens.

ZKTX lets people hold, send and trade Robinhood Chain tokens through shielded notes. Users keep the tokens and wallets they already use. The privacy layer sits between the public wallet and public market.

01 · WHAT IT IS

A private account layer for RH tokens

ERC-20 balances normally belong to visible wallet addresses. ZKTX changes the ownership representation without changing the asset. A user deposits a token into the vault and receives an encrypted private note representing the same value.

From there, the note can be sent privately, used in a shielded swap, or converted back into public tokens. The vault holds the real ERC-20 reserves while zero-knowledge proofs control who may move them.

02 · WHY THIS DESIGN

Zcash solved the ownership problem

Zcash introduced a useful idea: value does not need to sit in a public account to remain provably valid. It can live in a private note. The chain records a commitment to that note, and a zero-knowledge proof authorizes each spend without revealing the note owner.

ZKTX uses that model because it fits the problem better than temporary wallets, centralized ledgers or a second private liquidity pool. Temporary wallets remain traceable. Centralized ledgers require custody. A separate pool needs platform liquidity and becomes an isolated market. Shielded notes keep ownership private while the underlying tokens remain backed inside an onchain vault.

Inspired by Zcash, built for RH assetsZKTX does not use ZEC, require a Zcash wallet or bridge tokens to another chain. It applies the shielded-note pattern to Robinhood Chain ERC-20 tokens.

03 · PRIVATE NOTES

Your balance becomes a secret you control

A note contains the asset, amount, owner key and random blinding value. It is also bound to Robinhood Chain and the deployed vault, preventing reuse somewhere else. Only its Poseidon commitment is recorded publicly.

commitment = Poseidon(
  chainId, vaultAddress, token,
  amount, ownerPublicKey, blinding
)

When the note is spent, the browser creates a nullifier. The contract can recognize a repeated nullifier and reject double spending, but it cannot use the nullifier to identify the original commitment.

nullifier = Poseidon(commitment, ownerSecret, chainId, vaultAddress)

04 · USER FLOWS

What a user actually does

  1. Add a private balance

    Choose a token and amount. The wallet approves and deposits it. The browser creates the secret note and encrypts it with a key derived from the connected wallet.

  2. Private send

    Choose a recipient. A proof spends the existing note and creates a recipient note plus private change. The public chain sees a valid vault state transition, not a wallet-to-wallet token transfer.

  3. Shielded Swap

    Choose Buy or Sell and the desired token. The vault executes through existing RH liquidity, then returns the real proceeds as a new private note.

  4. Unshield to wallet

    Open the private portfolio, select a note and choose a destination. The proof authorizes the vault to release the underlying ERC-20 tokens.

05 · SHIELDED SWAPS

Use the real market without exposing the originating wallet

ZKTX does not create an isolated exchange and does not ask the platform to take the other side. It routes through existing Robinhood Chain liquidity. Direct V3 pools are used when available, with aggregated RH routing for compatible V4 and multi-hop paths.

The input comes from a private note. The vault becomes the visible market participant. Each order executes in 3 to 7 variable slices. When several traders are active together, their slices naturally overlap in the same rolling window. After execution, the actual proceeds settle into a new encrypted note owned by the user.

A public AMM trade cannot be removed from the chain. ZKTX instead breaks the direct identity link: the pool sees the ZKTX vault trading, while the user's input ownership and resulting ownership remain in private notes.

Privacy becomes stronger when unrelated users transact during the same period. Overlapping variable slices make simple wallet-to-trade matching harder without forcing everyone to wait for a scheduled batch.

07 · PORTFOLIO AND RECOVERY

The browser is the private wallet

The private portfolio is reconstructed from encrypted note records stored on the user's device. A deterministic key derived from the connected wallet decrypts those records locally. The key is never sent to the server, and there is no separate password to remember.

This design removes server custody, but it also gives the user real responsibility. A commitment cannot reveal its note secret. If both the encrypted note record and its recovery backup are lost, the operator cannot recreate access to that value.

Back up before moving meaningful valueKeep the encrypted recovery export and wallet backup in safe locations. Test recovery with a small note before relying on it.

08 · UNDER THE HOOD

The parts that make it work

Browser wallet

Creates secrets, encrypted notes, commitments, nullifiers and Groth16 proofs.

Shielded vault

Holds the ERC-20 reserves, verifies proofs and records commitments and nullifiers.

Merkle indexer

Rebuilds the commitment tree from vault events and supplies membership paths.

Relayer

Simulates and broadcasts valid private actions while the platform pays gas.

Market keeper

Executes approved routes in variable slices and records the real output.

Routing adapters

Connect the vault to compatible direct and aggregated RH liquidity.

The circuits enforce note ownership, membership, amount conservation, unique nullifiers, correct outputs and deployment binding. The contracts enforce the same public inputs on Robinhood Chain.

09 · FEES AND FLYWHEEL

Execution funds the protocol token

A Shielded Swap charges a 1.5% total fee. The execution allocation covers routing and operation. The protocol allocation buys ZKTX through the approved market route and permanently burns it.

WHY NOT ANOTHER WALLET?

A fresh wallet changes the address, not the public trail

Sending tokens to another wallet, selling them in batches and withdrawing the proceeds can resemble the ZKTX flow at a glance. The difference is that the intermediate wallet creates an explicit public chain of ownership.

Manual wallet route

The original wallet visibly funds the intermediate wallet. That wallet visibly trades, then visibly sends the proceeds onward. Amounts, timing and addresses can connect the complete path.

ZKTX route

The deposit enters a shared vault and becomes a private note. The vault trades as the public participant. Proceeds return to private ownership rather than a dedicated intermediate wallet.

No wallet farm

The user does not need to create, fund, secure and operate temporary wallets for every transaction.

Shared activity matters

Privacy is strongest when unrelated users share the vault and their variable execution slices overlap.

Not total invisibilityDeposits, market swaps and withdrawals remain public. ZKTX breaks the explicit ownership link between those events. When only one person is active, timing and amount analysis can still make correlation easier.
