ZKTX DOCUMENTATION · ROBINHOOD CHAIN

Zcash-style privacy for Robinhood Chain tokens.

ZKTX adapts the shielded-note model—commitments, nullifiers, Merkle membership and zero-knowledge proofs—to standard RH ERC-20 tokens. Users keep their existing token and wallet: no ZEC, bridge, wrapper purchase, or pre-swap is required.

Experimental mainnet pilotThe Shield interface now generates its proof in the browser, requests token approval and deposit signatures from the connected wallet, and stores the encrypted note only after confirmation. A deliberately tiny WETH/USDG mainnet lifecycle has passed, but the deployment still uses development proving keys and strict reserve caps; it must not secure material value. Review the onchain evidence.

02 · OVERVIEW

The simple model

A user deposits the RH token they already own. Their browser creates a Zcash-style secret note representing ownership of that balance, while the vault holds the original ERC-20 reserve. The chain stores a commitment instead of a public user balance. Later actions consume notes and create new notes while a zero-knowledge proof demonstrates that every rule was followed.

Public tokendepositVault reservecommitmentPrivate notesproofNew notes or withdrawal

The vault never creates underlying tokens. Its public token reserves must always cover the total value represented by unspent private notes.

02A · DESIGN ORIGIN

Borrow the privacy model, not the ZEC asset

ZKTX does not bridge ZEC onto Robinhood Chain and does not require a Zcash wallet. It adapts the architectural concepts behind shielded payments to an EVM-compatible vault for native RH tokens.

03 · ARCHITECTURE

Protocol components

Browser wallet

Creates secrets, commitments, nullifiers, proofs, and encrypted note backups. Sensitive note data remains in the browser unless the user explicitly exports it.

Shielded vault

Custodies supported ERC-20 assets, verifies proofs, tracks roots and nullifiers, enforces reserve caps, and releases tokens during valid withdrawals.

Circuits

Prove note membership, ownership, correct nullifiers, asset and amount binding, conservation of value, and valid output commitments.

Indexer

Reads vault events, rebuilds the commitment tree, records spent nullifiers, and supplies Merkle paths required to create proofs.

Relayer

Simulates and broadcasts approved private transfers and withdrawals so users do not need a separate public gas-paying wallet for each action.

Market executor

Executes shielded intents in 3–7 public PONS slices, immediately buys and burns ZKTX from the 1% protocol fee, then returns actual proceeds to private notes.

04 · PRIVATE NOTES

The Zcash-style object that replaces a public balance

A note commits to the Robinhood chain ID, vault address, asset contract, amount, owner public key, and random blinding value. The chain stores the resulting Poseidon hash, not the private fields.

commitment = Poseidon(
  chainId,
  vaultAddress,
  assetAddress,
  amount,
  ownerPublicKey,
  blinding
)

Binding the chain and vault prevents a proof or note from being replayed in another deployment. The nullifier binds the commitment to the owner secret and identifies a spend without revealing which commitment was spent.

nullifier = Poseidon(commitment, ownerSecret, chainId, vaultAddress)
Back up note secretsLosing the encrypted note data or its password can make the shielded balance unrecoverable. The operator cannot reconstruct a user secret from an onchain commitment.

05 · TRANSACTION FLOWS

Deposit, send, and withdraw

  1. Shield

    The user approves the vault and submits a deposit proof. The proof binds the deposited asset and public amount to the hidden note. The vault transfers the tokens, checks its reserve cap, appends the commitment, and records a new Merkle root.

  2. Private send

    The owner proves membership and knowledge of the note secret. The circuit consumes the note, creates a recipient note and a private change note, and proves that the output amounts equal the input amount. The vault records the nullifier and two new commitments.

  3. Withdraw

    The owner proves an unspent note exists under a known historical root and binds the proof to the public asset, recipient, and amount. The vault marks the nullifier spent and releases the original ERC-20 tokens.

06 · WITHDRAWAL PLANNING

Reducing simple boundary correlation

A single deposit followed by an equal withdrawal to one wallet is easy to correlate. ZKTX therefore plans withdrawals across two to four user-controlled destinations, uses standard denominations, applies independent delay windows, and retains unmatched value as private change.

Example

A shielded balance of 12,347 units could produce standardized withdrawals totalling 12,000 units across several destinations. The remaining 347 units stay shielded. The number and timing of outputs should vary across users.

The vault recognizes historical Merkle roots, allowing a proof created for a valid earlier root to remain usable after unrelated commitments are appended. Every root accepted by the vault must have been created by a verified state transition.

Not anonymity by itselfSplitting and delaying withdrawals weakens basic amount-and-time matching. It cannot guarantee anonymity, especially when pool activity is low or a user follows a distinctive pattern.

07 · SWAPS

Swap RH tokens as shielded notes

Atomic private swaps

A maker locks a shielded note into exact order terms: requested asset and amount, maker receive key, deadline, nonce, and a cancellation key. A taker can fill only those exact terms. One proof consumes the maker and taker notes, pays the maker and taker as new private notes, and returns any taker change.

The maker never shares the cancellation secret. A separate cancellation proof lets only the maker consume an unfilled order and recreate the original sell balance as a private refund note. Both fill and cancellation use the same nullifier, so only one can succeed.

Sliced PONS market execution

A market-order proof privately spends one shielded note while binding the public pair, input, minimum net output, deadline, and a secret settlement key. The keeper submits 3–7 variable slices, at most one per block. Each public pool trade remains visible as ZKTX adapter activity; the mechanism obscures the originating wallet but cannot make AMM reserve changes invisible.

The fee is fixed at 1.5%: 0.5% remains in the quote asset for execution costs and 1% immediately buys ZKTX and calls its native burn function. After the final slice, the user waits 30 seconds and proves two new notes: actual net proceeds and any unspent refund. The protocol never promises a fixed fill or carries market-maker inventory risk.

PONS V2 orders route through the launch's bonding curve before graduation and its official-hook Uniswap V4 pool afterward. Native-ETH launches are wrapped at the vault boundary. The browser flow is implemented but only becomes live when final proof artifacts, contracts, relayer, and keeper are configured.

08 · PROOF SYSTEM

Groth16 over BN254

The current circuits use Circom, Poseidon hashes, a depth-20 commitment tree, and Groth16 proofs on BN254. Separate verifiers are used because each circuit has a different public-signal layout.

09 · CONTRACTS

Vault controls and invariants

  • Only explicitly supported assets can enter or leave.
  • Every supported asset has an owner-configured reserve cap.
  • Commitments cannot be inserted twice.
  • Nullifiers cannot be spent twice.
  • State transitions must start from the current root.
  • Withdrawals may reference only roots previously recorded by the vault.
  • Token reserves are tracked and checked before release.
  • Deposits and transfers can be paused by the owner.
  • External token transfers use return-value checks and reentrancy protection.

The pilot owner is an encrypted server-held wallet. Control should be transferred to a multisig before broader usage.

10 · SERVICES

Indexer and platform-funded relayer

The indexer reconstructs the commitment tree exclusively from verified vault events. It persists commitments, nullifiers, the last indexed block, leaf count, and current locally derived root.

The relayer accepts strictly validated private-action payloads, simulates the contract call, applies per-IP limits, and broadcasts only if simulation succeeds. Its signing key is loaded from server configuration and is never sent to the browser. The keeper separately simulates each exact slice, derives a protected buyback minimum from the simulated burn amount, and broadcasts only successful slices.

Platform-funded gas improves usability and avoids forcing the recipient to acquire RH gas before withdrawing. It also creates abuse and availability risks, so production requires quotas, monitoring, multiple relayers, and a defined shutdown policy.

12 · SECURITY

Threat model

Protected against

Commitment forgery, unbalanced private transfers, cross-vault replay, cross-chain replay, double spending, unsupported assets, reserve-cap overflow, and invalid proof submission.

Not automatically protected against

Device compromise, password loss, malicious browser extensions, traffic analysis, IP logging, timing correlation, unique amounts, coercion, compromised setup parameters, or contract/circuit implementation bugs.

Trusted setup

Groth16 requires a setup. Final keys are generated after the circuits are frozen: verify phase 1, run a multi-party phase 2 for each circuit, apply a public beacon, verify the transcripts, and publish the artifacts. PONS does not issue these keys. Development keys remain trusted and unsuitable for public funds.

Unaudited release

The requested release skips independent audits. Passing tests is not an audit, and the circuits, generated verifiers, PONS routing, client cryptography, relayer, keeper, and operational setup may contain value-losing defects. The deployment acknowledgement records acceptance of this risk rather than claiming review.

13 · OPERATIONS

Capped mainnet pilot

  1. Configure

    Set the final token, quote asset, wrapped native, PONS V2 factory, small reserve caps, owner, verifier addresses, deployment block, RPC endpoint, relayer, and keeper.

  2. Deploy paused

    Deploy verifiers, V2 adapter, and vault; verify bytecode and PONS dependencies; register tokens and caps; then reconcile the genesis root before enabling deposits.

  3. Canary testing

    Perform tiny curve and graduated-pool buys and sells, buyback burns, settlement, expiry refunds, and recovery tests. Compare roots and reserves after every step.

  4. Monitor

    Alert on root divergence, failed simulations, stalled orders, graduation gaps, cap pressure, RPC disagreement, burn mismatch, and reserve discrepancies.

  5. Expand carefully

    Raise caps only after final-key verification, stable reconciliation, and a published incident-response process. This release remains explicitly unaudited.

September 23 WETH/USDG canary

The live Robinhood deployment completed real WETH and USDG deposits, a relayed private transfer, withdrawal to a fresh wallet, a private WETH/USDG RFQ settlement, order cancellation, and replay-rejection check. The final onchain commitment root matched the independently computed root, with 23 commitments indexed. Test amounts were intentionally tiny and caps remain restrictive.

14 · LIMITATIONS

Important realities

  • ZKTX does not make deposits or withdrawals invisible.
  • Small anonymity sets allow strong statistical inference.
  • Variable slices and delays reduce correlation but do not eliminate it.
  • A relayer can observe request timing and network metadata unless additional transport privacy is used.
  • Every public PONS slice and immediate buyback remains visible and may reveal the aggregate order when only one user is active.
  • Market intent pair, input, minimum output, and deadline are public, although the shielded note owner is not.
  • Local encrypted storage is only as safe as the device and password; losing settlement secrets can strand proceeds.
  • The browser market flow remains gated until final keys and production services are configured.
  • The current proving setup is for development validation, not trust-minimized production.
  • The implementation has not received an independent security audit.

15 · GLOSSARY

Key terms

Commitment
A hash representing a private note without revealing its contents.
Nullifier
A unique value published when a note is spent, preventing reuse.
Merkle root
A compact fingerprint of every commitment currently recorded in the tree.
Witness
The private information supplied to a circuit to generate a proof.
Relayer
A service that submits a valid transaction and pays public network gas.
Anonymity set
The group of plausible users or notes among which activity may be hidden.
Private change
Unwithdrawn value returned to a new private note controlled by the user.
Trusted setup
The parameter-generation process required by Groth16.
